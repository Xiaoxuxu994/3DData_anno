# 已知问题与下一步

按优先级排序。每做一个实验，在 `docs/experiments/LOG.md` 和 `experiments.csv` 里追加一条（编号接着 E14），被采纳的改动要更新 `configs/pipeline_v13.yaml` 的版本号和参考指标，并跑 `tests/`。

## 1. 米制尺度仍有 25% 失败（最大问题）

- A 组 v1.3 尺度失败率 25%（|尺度 − 1| > 10%），米制 AbsRel 0.069。
- 例：KITTI 07 轨迹形状正确，但尺度偏小约 30%：ViPE 的 k_traj ≈ 2.9 与 k_depth ≈ 1.15 不一致，几何平均后仍不准。
- 动态物体多时最先崩（牛津街人群 k = 7.5）。
- 方向：按场景类别选择 k_depth / k_traj；引入米制深度模型（MoGe-3、DA3-Metric）投票；把 k_depth 与 k_traj 的分歧作为质检项。

## 2. 内参“看起来合理但错了”（E14，建议下一个做）

- 门控只拦离谱值；驾驶等前进运动场景，ViPE 可能给出错误但在 [25°, 130°] 内的 HFOV（BTbk：33° vs 实际约 61°）。目前由质检拒掉，损失产出（驾驶类拒绝率最高）。
- E13 的焦距扫描（K × s 重算 Pi3X，看自洽性）在 KITTI 上能找回真值附近（+2–8°）。
- 计划：3 档扫描（s = 0.6 / 1 / 1.6）+ 抛物线拟合，约 57 GPU 秒 / 段，只在驾驶类或 K 分歧 > 13.2° 时触发；先在全部 KITTI / vKITTI2 / TartanAir 上验证，再决定是否覆盖 ViPE K。

## 3. 质检阈值是样本内定的

- v1c 的三个阈值只在 64 段有真值片段上拟合；需要 ④ 人工抽检的结论（复核页）来校准，并统计自校验与人工结论的一致率。
- 盲区：几个方法一起错时查不出；剪辑、变焦、航拍靠旗标只抓到约 60%。

## 4. 筛选层漏网

- 隐藏切镜（柔和转场）TransNetV2 会漏；夜雨模糊、密集人群这类应在筛选层拒掉，现在靠质检兜底，浪费打标算力。
- 筛选 P/R 的“真值”是设计的难例加 14 条 AI 补充标注，尚未人工确认。

## 5. 成本

- ViPE 占每段 GPU 时间约一半（43.8 / 85 s）。可尝试：更低分辨率 / 隔帧的适用范围、用 Pi3X 位姿初始化 BA、只在需要尺度时跑 ViPE。
- 100 万输入段 ≈ 1.15 万 H200·h（8 卡约 60 天），产出约 20 万段；下载约 1 TB / 天也可能成为瓶颈。

## 6. 4D（动态）尚未开始

- 目前只做静态 3D：ViPE 的动态 mask 去掉行人，不输出动态物体的几何与运动。

## 7. ViPE 重跑不完全可复现

- 同一段重跑，ViPE 轨迹可能差 3–4%（驾驶片段明显），以 ViPE 为证人的 v1c 跟着波动；v1c 接近 1 的片段两次结论可能不同（回归测试里 KITTI 07 的 2 项 WARN 即此原因，标签本身一致）。
- 方向：证人信号多次运行取中位数，或固定 ViPE 的随机种子 / 确定性设置后再评估。
- `pipeline/run_batch.sh` 目前只开 1 个 ViPE worker；成本模型里的“每卡 2 并发”和慢速类别隔帧（E6b / E6c）还没自动化。

## 8. GLR 轨道（GLRMap 打标）还没在真实 GLRMap 上跑过

- 管线胶水（路由、抽帧、第一阶段出口关口、结果收集、质检分级、回退）在沙箱里用合成数据和 pycolmap 复刻的第一阶段测过；GLRMap 本体的命令行、稠密深度的文件布局是按文档推断的（`docs/GLR_INTEGRATION.md` §6 的核对清单）。
- 所有 GLR 阈值（路由、关口、分级）是预注册的起始值；Phase 0 要在已有的第一阶段输出上用 `tools/glr_gate_replay.py` 回放，达不到通过线就不让 GLRMap 上网络视频。
- 证人（ViPE、Pi3X ≈ 0.65% ATE）比 GLRMap 好的时候（0.05–0.2%）噪声大，v1c 只能抓约 3% 以上的粗错；分级 T1/T2 不等于精确。
- GLR 与 v1.3 的失败机制是否互补只是假设（回退策略依赖它），要在同一批有真值片段上同时跑两条线来验证。
- E15 沙箱（CPU，pycolmap 复刻）的结果在 `docs/GLR_E15_summary.html`（`docs/GLR_E15_沙箱测试报告.md` 是同一份的 Markdown 版）：18 条简单网络视频里 7 条过出口关口，11 条被拦；对照 16 条全部没能变成 GLR 标签。**这是复刻不是 GLRMap，VLM 是 Claude 替身**，结论见该页“限制”一节。

## 9. 筛选 OCR 阶段（`filter/s3_ocr.py`）的文本框面积在 int16 下溢出

- 在 `envs/ocr-venv.txt` 锁定的版本（paddleocr 3.7.0 / paddlepaddle 3.3.1 / paddlex 3.7.2）下，`TextDetection(...).predict(img)[0]["dt_polys"]` 的 dtype 是 **int16**；`(x1 - x0) * (y1 - y0)` 在 int16 标量下，框大于约 181×181 像素（面积 > 32767）就溢出（numpy 报 `overflow encountered in scalar multiply`）。例：1920×1080 帧里多边形 `[[717,190],[1281,217],[1271,418],[707,390]]` 算出 −200，真值 130872。
- 影响 `scores.json["ocr"]` 里的 `text_area_max / text_area_mean / bottom_band_area / corner_area`（`static_text_area` 走 `cv2.fillPoly` 的 int32 多边形，不受影响）。`decide.py` 的 `text_overlay` 规则里 `ocr.text_area_max > 0.3` 这一半，对恰好最该抓的大字幕 / 大叠字会少报甚至不触发。
- 沙箱里 12 条 DL3DV 难度片段的实测：2 条受影响，`text_area_max` 原样 0.0143 / 0.0619，改成 float 后 0.0972 / 0.1273（都没超过 0.3，所以决策不变）；其余片段没有大框，两种算法一致（`/tmp` 里的复核脚本见 docs/experiments/LOG.md E15）。
- 建议（未改，因为会改变已记录的筛选分数和可能的决策）：在循环里先 `p = p.astype(np.float64)`；在 C 组上对修复前后的 `text_area_*` 和 `decide.py` 决策做对比，写进 LOG 再决定要不要动 0.3 / 0.02 两个阈值。
- 顺带观察：`static_text_area > 0.02` 会误拒“前进运动 + 画面中央有一排亮窗”的片段（沙箱里教堂走廊那条：没有任何字幕或水印，三帧的中央窗户排被检成文字框，交集 2.7%）。前进镜头的远处结构在图像里位置基本不动，和“烧进画面的静态叠字”在这个统计量上很像；DL3DV 式前进 / 绕拍场景里可能系统性出现。

## 10. 网络视频上第一阶段的内参 K 基本不可观测（E15）

- 复刻第一阶段（PINHOLE，焦距自由）在 18 条简单网络视频上：有银参考的 14 条里 **11 条焦距与参考相差 > 10 %（中位数 43 %）**，其中 4 条通过了关口（静默错误），而轨迹本身大多是准的（11 / 14 条 Sim(3) ATE ≤ 3.27 %，中位数 0.28 %）。前进镜头、远景航拍里焦距常停在初值 1.2×长边附近，fx 与 fy 各自漂移，被 `fx_fy_mismatch` 拦下；国家公园峡谷航拍上复刻、银参考、GeoCalib 三者互不一致（f/W 0.27–0.38 / 0.89–1.4 / 0.83）。
- **换随机种子（v0b）结果和 v0a 一致**：焦距误差是确定的，重跑发现不了。**SIMPLE_PINHOLE（v1sp）不是修法**：16 条里 13 条过关口，但只有 3 条与银参考一致，静默错误从 4 条升到 10 条，因为它把 `fx_fy_mismatch` 这个“焦距定不下来”的警报关掉了，焦距误差还在。**把 GeoCalib 焦距当初值（v2prior）没有用**（优化器回到和 v0a 同样的解，14 条里静默错误 4 条）；**把 GeoCalib 焦距固定（v3fixed）最好**（14 条里 13 条过关口、6 条与银参考一致、焦距中位误差 11 %），但“一致”只是和另一次重建、一个单图先验一致；复刻、银参考、GeoCalib 三方对照里，只有两者一致时是（银参考 = GeoCalib）5 次、（复刻 = 银参考）1 次、（复刻 = GeoCalib）0 次，自由焦距的复刻最不可靠。
- v1c 的 K 容差（HFOV 13.2°，约 25 % 焦距）抓不到 10–25 % 的焦距错：联调演示里 mk_4206（焦距偏 22 %）以 T2 通过质检。
- 方向：焦距定不下来时（`fx_fy_mismatch`、焦距停在初值、`low_parallax`）不用 SfM 的焦距，改用图像级 K 证人的中位数（GeoCalib / Pi3X / DA3）作为固定内参，或先做 E14 的焦距扫描；在服务器上用真实 GLRMap 做 `docs/GLR_PHASE0_RUNBOOK.md` 的 0.2b 消融再定，不要在沙箱数字上定。

## 11. 前端对“淡水印”和“静态叠字”的两个盲点（E15）

- 独立核验发现 `ia_telangana` 带一条半透明频道水印（不透明度约 0.2–0.3，占画面 0.5 %，全程固定）：OCR 阶段和 VLM（接触表分辨率）都没看见，片段整条通过。时间中位数 / 标准差图上看得见，可以做成一个 CPU 上几秒的静态叠层检测。
- 反过来，`px_19834200`（教堂走廊，前进镜头 + 中央一排亮窗）被 `static_text_area > 0.02` 误拒（本页第 9 条已记同一现象）。两个盲点说明 OCR 的“静态文字”统计量同时有漏报和误报。
